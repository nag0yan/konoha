# Konohaのアーキテクチャ

## 現行の技術決定

| 領域 | 採用と理由 |
|---|---|
| 管理画面 | React + Vite。ローカルの対話画面にSSRやSEOは不要なため、Next.jsは採用しない。 |
| 制御API | Hono。ログイン、アプリの所有者確認、生成・起動・更新を担当する。生成コードは制御API上では動かさない。 |
| コード生成 | Bedrockの `Converse` を直接利用する。現行はソース生成と静的診断のフィードバックに限られ、AgentCoreの実行環境や管理ツールは不要。既定は東京リージョンの `jp.amazon.nova-2-lite-v1:0`。`AWS_REGION` と `BEDROCK_MODEL_ID` で上書きできる。 |
| アプリ実行 | Docker内のQEMUによるアプリ専用Linux VM。ブラウザ内のプレビューだけではサーバーコードを検証できない。ソフトウェア仮想化を使い、ホストのKVM権限は不要。 |
| 永続化 | PostgreSQLにユーザー、セッション、VMアプリのソースと版番号を保存する。これは制御側のDBで、生成アプリには接続させない。 |

```text
ブラウザ → React/Vite → Hono → Bedrock（生成）
                          ├→ PostgreSQL（認証・ソース保存）
                          └→ QEMU VM（起動・検証）
ブラウザ → 所有者専用のプレビューゲートウェイ → QEMU VM
```

## 作成・更新・復元

1. Bedrockが `server.mjs` を含むソースを返す。Konohaはファイルを検証し、固定設定のESLintで構文と未定義参照をチェックする。生成側の設定・プラグインは読み込まない。
2. 静的検査に失敗した場合、直前のソースと短い診断（ファイル名・行番号・ルール名・メッセージ）をBedrockに返して最大2回修正する。VM内の実行時エラーはこの自動修正の対象外。
3. 検査を通ったコードをVMで起動し、`GET /` が `200 text/html` を返すことを確認する。業務機能の正しさまでは検証しない。
4. 更新時は現在のソースと変更要望から候補を作る。稼働中の旧版はそのまま使え、起動確認に成功した場合だけソースと版番号を更新して同じURLを切り替える。失敗時は旧ソースを保持する。過去版の履歴・切り戻しは未実装。
5. VMは同時に2台まで、最大30分で終了する。稼働中のアプリの更新には候補用の空き枠が1台必要。停止後は保存したソースから再起動でき、Bedrockを再度呼ばない。ゲストの実行データは復元しない。

## 権限と公開範囲

- アカウントとアプリの所有者を区別する。VMプレビューは `http://<app-id>.localhost:3002` の別オリジンで、所有者のログインセッションに紐づく短命・一回限りのチケットで開く。VMアプリのメンバー共有は未実装。
- VMには外部ネットワーク、ホストのAWS資格情報、DB接続を渡さない。ゲートウェイは専用Unixソケット経由でアプリに接続する。
- 現行はローカル用。公開前には登録制御、利用量・費用制限、レート制限、監査、TLSが必要。AWS上のWeb層やVM実行基盤は未デプロイ。

## 将来のアプリ用データストア

ここは未実装で、現行の起動手順には含まれない。

| 案 | 判断 |
|---|---|
| SQLite/PGlite + S3複製 | 起動が軽く、使い捨てプレビューには候補。非同期複製で直近の書き込みを失う可能性があり、単一ライターと復元の検証が必要。 |
| Aurora PostgreSQL + アプリ別スキーマ | 永続的な運用データの候補。共通クラスタの容量・接続数・障害範囲を考慮し、スキーマ名だけでなくDBロールでも分離する。 |
| アプリごとのIaC | 専用リソースを作れるが、権限・費用・削除管理が重い。必要な場合に人が承認する構成に限る。 |

生成コードにDB管理権限は渡さず、信頼できるデータアクセス層で認証・認可を行う。DDLは実行用ロールから分け、破壊的変更には承認と復旧計画を求める。S3を使う場合は成果物とユーザーファイルを分け、アプリごとにアクセスを制限する。

## 廃止したプロトタイプ

- 定義ベースの予約テンプレート・共通CRUD・メンバー共有と、`handle(input)` / `render(result)` をDockerで動かす旧コード版は削除した。旧UI切り替えと旧APIは利用できない。
- 既存DBの旧テーブルやアプリ別スキーマは削除していない。旧データのVM版への移行は行わず、新規DBにも旧テーブルを作らない。
- AWSにデプロイ済みの旧定義生成AgentCoreに対応する [Terraform構成](../infra/aws/) と [エージェントのソース](../src/agent/) は、既存リソースの管理のために残す。現行アプリからは使わない。必要に応じて `mise exec -- npm run build:agent` で旧成果物をビルドできる。この整理ではAWSリソースやTerraformの状態は変更していない。
