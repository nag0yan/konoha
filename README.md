# Konoha: ローカルMVP

要望からBedrockでWebアプリのソースを生成し、アプリ専用のLinux VMで起動するローカルプロトタイプです。作成画面では定義やコードの形式を選ぶ必要はありません。**本番・インターネット公開には使えません。**

## 前提と起動

miseとDockerデーモンが必要です。Node.js、AWS CLI、Docker CLI、Docker Composeは[mise.toml](./mise.toml)でプロジェクトごとに固定しています。Dockerデーモン自体は別途必要です。

```sh
mise trust
mise install node aws-cli docker-cli docker-compose terraform
mise exec -- npm ci
mise exec -- docker-compose -p konoha-local up -d --wait
mise exec -- docker build --tag konoha-qemu:local infra/vm
```

別々のターミナルで次を実行します。

```sh
mise exec -- npm run dev:server
```

```sh
mise exec -- npm run dev
```

`http://127.0.0.1:5173` を開いて登録・ログインし、「色を変えながら線を描けるお絵描きアプリを作って」と入力します。「実行中」になったら「アプリを開く」を押してください。モデルは東京の `jp.amazon.nova-2-lite-v1:0`（変更可能）で、AWS認証が必要です。要望本文はBedrockに送られ、利用料金が発生します。機密情報は入力しないでください。

QEMUは x86-64 のソフトウェア仮想化で起動し、ホストのKVM権限は不要です。VMには外部ネットワーク、ホストのAWS資格情報、DBを渡しません。プレビューは `http://<app-id>.localhost:3002` で、Konohaにログインしたオーナーだけが開けます。リモート開発では3002番ポートも非公開で転送し、ローカル側のポートを3002にしてください。VMは同時に2台まで、最大30分で終了します。停止してもソースはPostgreSQLに残るので再起動できます。ゲストの実行データは保持されません。

作成したアプリの「アプリを修正」から、たとえば「消しゴムを追加して」と依頼できます。修正要望と現在の生成コードはBedrockに送信され、利用料金が発生します。修正版は別のVMで検証し、起動確認に成功したときだけ同じURLを新版に切り替えます。開いていた場合は再読み込みしてください。失敗時は元のソースを変更しません。実行中のアプリを修正するときは、検証用に空きVM枠が1台必要です。新版への切り替えでVM内の一時データは引き継がれません。アプリ用DB、AWSへの公開は未実装です。

起動前に、Konohaが固定設定のESLintでJavaScriptの構文と未定義参照を検査します。`server.mjs` と `server/` はNode.js向け、その他のJavaScriptとHTML内のスクリプトはブラウザ向けに検査します。生成コードの設定やプラグインは読み込みません。新規生成や修正版の生成で検査に失敗した場合、直前の生成結果とファイル名・行番号・ルール名・短い診断をBedrockに返して最大2回修正します。合格後にVMでHTTP応答を検証します。保存済みコードを修正せずに再起動するときはBedrockへ送信しません。実行時エラーは自動修正の対象外です。

QEMUの起動テストも行う場合は、イメージをビルドしてから `KONOHA_TEST_VM=1 mise exec -- npm test` を実行します。このテストはBedrockを呼び出しません。

終了時は各開発サーバーを停止し、DBを停止します。次のコマンドはデータボリュームを削除しません。

```sh
mise exec -- docker-compose -p konoha-local down
```

## 旧プロトタイプ（互換性確認用）

以下は旧来の定義生成・制限付きコードの説明です。必要な場合だけ `VITE_KONOHA_LEGACY_UI=1 mise exec -- npm run dev` で旧画面を起動します。既存のデータは新しい作成画面へ移行されません。

### Bedrockによる定義生成

`GENERATOR=template` を設定せず、利用するリージョンとモデルIDを指定してサーバーを起動します。AWS認証と対象モデルの利用権限が必要です。

```sh
AWS_REGION=ap-northeast-1 BEDROCK_MODEL_ID='<利用可能なモデルID>' mise exec -- npm run dev:server
```

必要に応じてAWS CLIのSSOログインを行ってください。モデル出力はJSON定義として検証されます。テーブルと項目の追加に対応し、削除や既存項目の型変更は拒否します。モデルの対応形式・リージョン・利用権限によって呼び出しが失敗する場合は、サーバーログを確認してください。コードを生成・実行する方式ではありません。

日付欄は、文字列型を維持したまま `widget: "date"` でカレンダー入力に切り替えられます。DBの列型や既存データは変更しません。AgentCoreモードでこの機能を使うには、対応版のエージェントのビルドと再デプロイが必要です。

東京リージョンでは `jp.amazon.nova-2-lite-v1:0` の推論プロファイルを利用できます。モデルの呼び出しには料金が発生します。

## AgentCoreとTerraform

[infra/aws](./infra/aws) には、AgentCoreの定義生成エージェント、限定的な実行ロール、非公開の成果物バケットを作るためのTerraform構成があります。これはAWS全体のMVPではなく、Web Function、MicroVM、Aurora、Cognitoは含みません。東京リージョンでAgentCoreをデプロイし、ローカルAPIをプロセス内で呼び出す統合検証で、AgentCoreによる定義生成、DBへの保存・読み出し、スキーマ追加後の既存データ保持を確認しました。ブラウザからのAgentCore連携は未検証です。

構成を確認する場合は、まずバンドルを作成します。

```sh
mise exec -- npm run build:agent
mise exec -- terraform -chdir=infra/aws init
mise exec -- terraform -chdir=infra/aws validate
mise exec -- terraform -chdir=infra/aws plan -var='aws_account_id=<12桁のアカウントID>'
```

プランを確認するまでは適用しないでください。適用するとAWSのリソース使用料が発生します。Terraformの状態ファイルはローカルに保存されるため、取り扱いとバックアップに注意してください。バージョニングされた成果物バケットは、オブジェクトが残っている場合、通常の `terraform destroy` では削除されません。

デプロイしたAgentCoreをローカルのアプリから利用する場合の設定は次のとおりです。

```sh
GENERATOR=agentcore AWS_REGION=ap-northeast-1 AGENTCORE_RUNTIME_ARN='<AgentCore runtime ARN>' mise exec -- npm run dev:server
```

呼び出し元にも対象ランタイムの `bedrock-agentcore:InvokeAgentRuntime` 権限が必要です。エージェントは定義生成のみを行い、DB操作やデプロイ権限は持ちません。

## コード編集・承認のローカル実験

トップページの「アプリを作成」から直接コード版を作れます。既存アプリに別途コード版を追加することもできます。実行基盤は予約などの業務データを知らず、生成された JavaScript の `handle(input)` に JSON を渡し、`render(result)` が返す制限付きの表示内容を描画します。たとえば予約の空き枠なら `{"slots":["09:00","10:00"],"booked":["09:00"]}`、在庫の集計なら `{"items":[{"name":"サンプル","quantity":3}]}` が使えます。

1. `mise exec -- docker pull node:24-alpine` で実行イメージを用意します。
2. APIを `KONOHA_CODE_MODE=fixture GENERATOR=template mise exec -- npm run dev:server` で起動します。コード版が有効なら、ログイン済みユーザーは個別の許可設定なしで作成できます。
3. トップページの「アプリを作成」で「コード版」を選び、要望を入力して「生成してプレビュー」を押します。サンプルJSONは任意です。編集と承認はアプリのオーナーだけが行えます。承認するとアプリのメンバーが公開版を閲覧できます。この公開はローカルアプリ内の切り替えで、インターネットへのデプロイではありません。従来のひな形を使う場合は「定義ベース」を選びます。

`fixture` は見出しの変更だけを再現し、AIやAWSを呼び出しません。AIでコードを編集するには `KONOHA_CODE_MODE=bedrock AWS_REGION=ap-northeast-1 BEDROCK_MODEL_ID=jp.amazon.nova-2-lite-v1:0` を指定します。この実験の編集先はAgentCoreではなくBedrockです。変更依頼・サンプルJSON・直前の実験コードがBedrockに送信されるため、機密情報や実データを含めないでください。

コードと検証用サンプルはアプリごと・リビジョンごとにPostgreSQLへ保存します。実行用コンテナにアプリのDB、本番データ、AWS認証情報、ホストのファイルは渡しません。検証はサンプルと空入力での実行・出力形式の確認で、業務ロジックの正しさは保証しません。任意のブラウザJS、独自のHTTPルート、DB操作、外部依存、本番運用には未対応です。この機能はデフォルトで無効で、本番モードでは利用できません。

## 検証

DBを起動した状態で実行します。テストは一時ユーザーとアプリを作成し、終了時にそれらを削除します。

```sh
mise exec -- npm run build
mise exec -- npm test
```

テストは、メンバー間の共有・非公開、アプリ外ユーザーの拒否、メンバー削除、既存データを保持した項目追加、および不正な定義の拒否を確認します。

コード版の統合テストも実行する場合は、ローカルDBと `node:24-alpine` を用意した上で `KONOHA_TEST_CODE=1 mise exec -- npm test` を実行してください。

## 制限

- 認証はローカル用で、誰でも登録できます。メール認証、招待・承認制、AI利用量の制限、パスワード再設定、レート制限、監査、TLS終端はありません。本番公開前に利用者の制御と費用対策が必要です。
- テキスト・数値・真偽値を扱うCRUDに限定し、外部キーや画像、ファイル、任意の実行コードには対応していません。
- 既存データに対する公開範囲の変更は個別編集で行います。アプリのデフォルト変更は既存レコードには適用されません。
- DBや生成定義の自動バックアップ、復旧、承認フロー、プレビュー環境、旧バージョンへの切り戻しはありません。
- 開発用DBには固定のローカル専用パスワードを使用し、ポートはループバックにのみ公開します。

## 目標アーキテクチャ

以下は将来の構成であり、現在の実装を表すものではありません。

```text
ユーザー → 認証・認可付きWeb Function → AgentCore → 制限付き管理ツール
                    │                                    │
                    └→ アプリ専用MicroVM → データアクセス層 → Aurora PostgreSQL
                                               └→ S3（アプリ成果物・ファイル）
```

### DB方式と権限境界

| 方式 | 利点 | 課題 | 位置付け |
|---|---|---|---|
| SQLite/PGliteとS3への複製 | 軽量で起動しやすい | 非同期複製時のデータ損失、単一ライター保証、復元検証が必要 | 使い捨てプレビューやローカル開発 |
| Aurora Serverlessとアプリ別スキーマ | SQL、トランザクション、バックアップ、動的なテーブル追加 | 共通クラスタの障害・費用・接続数・認可境界 | 運用データの推奨構成 |
| エージェントによるIaC | 専用のAWS資源を構築可能 | 権限、作成時間、費用、削除管理 | 人が承認した特別な構成のみ |

SQLiteのS3複製は同期コミットを保証しないため、MicroVMの停止や障害時に直近の書き込みが失われ得ます。Auroraを事前に用意し、アプリごとにスキーマを追加することで、DBインスタンスの作成を毎回待たずに済みます。Auroraの停止・再開時間やモデル生成時間を含めた公開完了時間は保証せず、実測します。

複数ユーザーではアプリ単位にオーナーとメンバーを管理します。各レコードは共有または非公開とし、非公開は作成者とオーナーのみ閲覧・編集できます。個人アプリはメンバーを持たないアプリとして扱います。

- 認証済みユーザーとアプリ所属の確認は信頼できるWeb層が行い、クライアント指定のユーザーIDを信用しません。
- 生成されたコードにはDB管理者権限を渡しません。信頼できるデータアクセス層がリクエストごとに認証・所属・レコードの公開範囲を確認し、DB操作を制限します。メンバー除外後のアクセスも拒否します。
- DBスキーマごとに実行用の権限を分け、DDLは別のマイグレーション権限で実行します。スキーマ名だけで隔離できたとみなさず、DBロールと権限を検証します。
- S3はアプリごとにアクセス範囲を制限し、成果物とユーザーファイルを分離します。MicroVMには対象アプリの必要最小限の権限だけを与え、通信先を制限します。
- 現在のローカル実装は、共通の信頼されたサーバーがDBアクセスを行います。上記のAWS用権限分離や生成コードの隔離を実現したものではありません。

### UIと実行環境

MVPの管理画面はReact + Vite + Honoを採用します。軽量な対話画面とプロキシを構成しやすいためです。Next.jsは公開ページのSEOやSSRが必要になった場合に再検討します。

ブラウザ内プレビューは画面の早期確認に使い、本番の認可や永続化の検証とは区別します。将来、生成コードをブラウザで実行する場合は制御画面と別オリジンの制限付きiframeを使います。DB、API、サーバー処理を含む実行はアプリ単位のMicroVMで隔離します。現在は生成コードの実行ではなく、検証した定義を共通UI/APIで処理しています。

### ライフサイクル

1. オーナーの要望から、エージェントがアプリ定義と変更案を生成し、検証する。プレビューは本番データから分離する。
2. 承認されたDB変更を専用権限で適用し、成果物とバージョンを保存する。起動とヘルスチェック後にアプリを公開する。
3. 機能追加時は現行バージョンと比較し、テスト後に追加的なスキーマ変更を適用する。削除や型変更などの破壊的変更には承認と復旧計画を必要とする。
4. アプリ単位で変更を排他制御し、変更履歴と成果物の対応を記録する。障害時は旧コードに戻せるようにし、DB変更については互換性を確保するか、別途検証した復元手順を使う。
5. 短い休止はMicroVMの停止・再開を利用し、VM終了後は保存済み成果物と外部DBから新しいVMを復元する。バックアップからの復元も定期的に検証する。

ローカル実装が備えるのは、定義の履歴保存、追加的なDB変更、DB再起動後のデータ保持です。承認、独立プレビュー、AWS上のVM再作成、バックアップ復元、切り戻しは未実装です。

### MVPの範囲とディレクトリ

まず予約管理を対象に、オーナーとメンバーによる登録・共有・非公開、データ保存、メモ項目の追加、再起動後の読み出しを検証します。画像編集、IDE、自由なインフラ作成は対象外です。

```text
src/client/       Reactによる管理画面・共通UI
src/server/       ローカル認証、データアクセス、定義生成
src/agent/        AgentCore HTTP契約と生成エージェント
src/shared/       検証するアプリ定義
infra/aws/        AgentCoreと成果物バケットのTerraform構成
compose.yaml      ローカルPostgreSQL
```

次の段階では、認証付きWeb層、アプリ単位のMicroVM、Aurora、S3を追加し、AWS上で生成から変更・復元まで通して検証します。任意コード実行を有効にする前に、分離、権限、外向き通信、依存関係と費用の制限を実装する必要があります。
